# 2026-08-17：TW OTP 中斷的排查與修復

> **本次修復的協定研究幾乎全部來自上游 [`pungin/Beanfun`](https://github.com/pungin/Beanfun)。**
> `get_webstart_otp_v2.ashx` 的存在、`LaunchTicket` 的解碼演算法、`Referer` 檢查、
> GGM 客戶端驗證參數、以及長輪詢與密碼無關這個判斷,都是他們當天做出來的。
> BeanyCord 只是站在那份成果上,補上一個對我們才成立的最後一哩。
>
> 逐項出處見文末〈致謝與出處〉。

## 症狀

Discord bot 取 OTP 時回:

```
❌ 取得 OTP 失敗
原因:Error: Secret codes do not match!
```

重新登入無效,所有帳號與遊戲皆然。

**現況:已修復並實際登入遊戲驗證通過。**

## 結論(先講答案)

**根因只有一行**:step 5 的 `SecretCode` 參數必須送 **portal 自己的 `bfSecretCode`
cookie**,而不是 `get_cookies.ashx` 回傳的 `m_strSecretCode`。

兩者是不同的值,因為 `get_cookies.ashx` 位於 **newlogin 主機**
(`tw.newlogin.beanfun.com`),回的是那台主機 session 的 secret;而 step 5 打在
portal(`tw.beanfun.com`),驗的是 portal 的 cookie。

```ts
// src/beanfun/otp.ts
const code = (await client.readSecretCode()) ?? pageCode;
```

WPF 原始客戶端與 Rust 移植都送頁面那個值,所以這是 BeanyCord **刻意偏離 1:1 移植**
的一處。

同一個 session、相隔數秒的並排實測:

```
secret=page m_strSecretCode        ppppp=hardcoded constant -> 0;        Error: Secret codes do not match!
secret=page m_strSecretCode        ppppp=blob-supplied      -> 0;        Error: Secret codes do not match!
secret=portal bfSecretCode cookie  ppppp=hardcoded constant -> *** OK — ENVELOPE RETURNED ***
secret=portal bfSecretCode cookie  ppppp=blob-supplied      -> *** OK — ENVELOPE RETURNED ***
```

### 為什麼 cookie 要取「第一個」

jar 裡同時存在兩個 `bfSecretCode`,**值不同**:

```
bfSecretCode(domain:.beanfun.com)     ← 這個
bfSecretCode(host:tw.beanfun.com)
```

ASP.NET 的 `Request.Cookies["bfSecretCode"]` 讀的是 Cookie 標頭中的**第一個**,而
`got` 送出的順序與 tough-cookie 的 `getCookies()` 順序一致。所以取索引 0 拿到的,
正是伺服器會拿去比對的那一個。

## 修正的實際範圍:一行

**legacy 流程真正需要改的,只有 `SecretCode` 的來源。** 加起來大約 15 行,包含
`readSecretCode()` 這個 helper。

但這只涵蓋走 legacy 的遊戲。同一個帳號下的**另一個遊戲已經遷移到 v2**,對它而言舊
端點是真的封了 —— 所以 v2 那條路並不是備用品,是必要的。兩條路都需要,而且都已在
真實伺服器上驗證通過(見〈兩條路都在真實伺服器上通過了〉)。

這點值得寫下來,因為我一開始照著上游文件多改了幾處,事後量測顯示那些都不需要 ——
其中一處甚至是負債。判斷依據是那次掃描:**探針在整條鏈上一個 `Referer` 都沒送**,
而 step 3 回 `Success`、step 5 回信封。

| 改動 | 證據 | 判定 |
| --- | --- | --- |
| `SecretCode` 改讀 portal cookie | 掃描四格直接分出勝負 | **必要** |
| step 3 加 `Referer` | 沒送也回 `intResult: 1, Success` | 不需要,已移除 |
| step 4 加 `Referer` | 見下 | 不需要且有害,已移除 |
| 用 blob 的 `ppppp` | 寫死常數與 blob 值**都被接受** | 不需要 |
| 依解碼結果路由 | — | 只有引入 v2 後才需要 |
| v2 路徑 + 解碼器 | 此帳號的**另一個遊戲**確實走這條 | 必要(見下) |
| v2 POST 帶 CV/Hash | v2 端點確實檢查 | **必要** |
| legacy GET 帶 CV/Hash | 三個 arm 全回信封,**含故意寫錯的那組** | 不需要但無害,保留(見下) |

最後一列原本和它上面兩列綁成同一格「v2 路徑 + 解碼器 + CV/Hash」,判定「必要」。
那是真的 —— 對 v2 而言。但**一列只能有一個判定**,於是 legacy 那一份跟著搭了便車,
逃過了 `52d4d9d` 那次審計(那次只查了 `Referer` 和 `ppppp`)。綁在一起的改動不能一起判。

### legacy 的 `CV`/`Hash` 為什麼留著

程式碼裡原本寫的是「GGM 1.5.x 之後舊端點也要這個,不送會被拒」。這是從上游筆記外推
的,而且方向和當時手上的資料相反 —— 找到 secret 修復的那次掃描**一個 `CV` 都沒送**,
照樣拿到信封。

補測三個 arm(`probe:otp`,只變動這個三元組,600309_A2):

```
identity=omitted              -> *** OK — ENVELOPE RETURNED ***
identity=ours (pinned pair)   -> *** OK — ENVELOPE RETURNED ***
identity=deliberately wrong   -> *** OK — ENVELOPE RETURNED ***
```

第三個 arm 是關鍵:格式正確但絕不可能是 beanfun 出的版本(`CV=9.9.9.9`、64 個 `0` 的
hash)。它被接受,代表這個端點**不讀這些值**,而不只是容忍它們。

判定因此和 `Referer` 不同。`Referer` 有量測到的成本(把一個免費的即刻失敗變成多秒
停頓),所以移除;這個沒有成本,所以留著 —— 讓請求長得像官方啟動器,對第三方 client
而言是面對風控時比較安全的形狀。

真正該記住的是另一半:**當 legacy 路線開始失敗時,GGM 的版本釘子不是嫌疑犯。** 只有
v2 會讀它。這正是 `ggmVerdict()` 印在 v2 拒絕旁邊、而不印在 legacy 拒絕旁邊的原因 ——
那個不對稱是對的。

### `Referer` 的真相,以及一個我自己種進去的成本

上游記載 `generic_handlers` 底下的處理器開始檢查 `Referer`,沒帶就回(HTTP **200**):

```json
{ "intResult": 0, "strOutstring": "[generic_handlers - get_result.ashx] Error: The URL referrer is null or from a different domain!" }
```

這在我們的程式碼裡隱形很久,因為 `ensureSuccess()` 只看狀態碼,而它回 200。

**但在 legacy 鏈上,只有 `get_result.ashx` 在意 —— 而它的答案正是我們不要的那個。**

- **不帶 `Referer`** → 伺服器秒退,零成本,step 5 完全不受影響
- **帶了 `Referer`** → 它**真的變成長輪詢並把連線掛住**,一次撞出 30 秒逾時

`get_result.ashx` 是啟動器的安裝檢查,與密碼無關 —— 上述掃描裡 step 4 四次全部失敗,
step 5 照樣回信封。所以加上 `Referer` 的淨效果,是把一個「本來就不需要成功」的請求
從「立刻失敗」變成「掛住連線」,再補一個逾時去圍堵它,**每次取 OTP 可能多付數秒,
換來的東西是零**。

現在 step 3 和 step 4 都不送 `Referer`,只有 v2 的 POST 送。逾時預算保留當防護網。

教訓很直接:**我加上那個標頭,依據的是上游文件的權威,不是量測** —— 而這整輪排查的
主題正好就是這件事。

### 路由要看「解碼結果」,不是「handoff 是否存在」

`game_start_step2.aspx` 會帶一個 `m_objData` 交接資料給原生啟動器 GGM。上游的判斷是
「有 `m_objData` → 走 v2 端點」。**這對瑪奇(`600309_A2`)不成立**:

```
decoded fields: ppppp, ServiceCode, ServiceRegion, ServiceAccount, CreateTime, BeanfunUrl, WebStartPatch
```

解得完美,但**沒有 `LaunchTicket`** —— 它交接的是 legacy 參數組。這種頁面送到 v2
端點沒有東西可以交換。所以路由條件改成「解出來有沒有 `LaunchTicket`」。

順帶一提,blob 裡那個 112 字元的 `ppppp` 與寫死的 64 字元常數**兩者都被接受**,
`ppppp` 從來不是問題。

### 拒絕訊息本身是可診斷的

| 回應 | 意義 |
| --- | --- |
| `0;        Query String Error` | 伺服器**不讀**這個請求 → 該遊戲已遷移到 v2 |
| `0;        Error: Secret codes do not match!` | 伺服器**讀了**,但某個值不對 |

(前面那 8 個空白是成功信封的 key 欄位被留空後拿來放錯誤訊息。)

上游看到的是前者,我們一開始是後者。**這個差異當時被當成雜訊,其實是最重要的線索** ——
它代表舊端點對那個遊戲根本沒死。

後來換遊戲測,**同一個客戶端在同一個 session 下把兩種訊息都拿到了**,這張對照表因此
不再是推論。

## 排查過程,以及三個被推翻的判斷

留下這段,是因為錯誤路徑比結論更有參考價值。

### 判斷一:「WebToken 漂移」— 錯

step 5 是唯一用 URL 參數而非 cookie 指認 session 的一步,而我們送的是登入時凍結的
`session.webToken`。上游 `account.rs` 明確記載 `auth.aspx` 會輪替 `bfWebToken`
cookie,而我們從不回寫。推論合理 —— 但一量就死:

```
session.webToken: 7ad5ebd604/32c
jar bfWebToken:   7ad5ebd604/32c   -> aligned
```

我當時還設計了一個「重新登入後立刻取 OTP」的判別測試,**那個測試設計是錯的**:
輪替點 `auth.aspx` 在每一條路徑上都跑在第一次 OTP 之前,所以無論結果如何都推翻不了
任何東西。

### 判斷二:「舊端點已退役」— 錯

照上游文件直接採信,還把「step 5 expected to fail no matter what we send it」印進了
探針輸出。實際上它對我們完全可用。

### 判斷三:「解碼器壞了」— 錯,而且錯在我自己寫的錯誤訊息

解碼器丟出 `no substitution table yielded a LaunchTicket`,於是我花了一整輪追解碼器。
真相是它**從頭到尾都在正確解碼**,只是我把接受條件寫成了內容判斷:

```ts
if (plaintext.includes('LaunchTicket=')) return plaintext;   // 舊:把「有沒有這個欄位」當成「表對不對」
if (looksLikeText(plaintext)) return plaintext;              // 新:可列印率 ≥95% 且含 '='
```

真實資料證明門檻分得很開:正確的表 **100%** 可列印,其餘八張全部落在 **43%** 附近。

現在 `LaunchTicket` 缺席時會列出實際有哪些欄位,這是「讀不到」與「讀到了但欄位不同」
的差別,有專屬測試保護。

## 真正讓事情收斂的:抓一次,離線窮舉

停止猜測的轉折點,是把工具做出來而不是再推理一輪。

```bash
npm run probe:otp -- --write   # 一次連外,落地原始位元組
npm run analyze:launch         # 之後全部離線,想跑幾次都行
```

`analyze:launch` 試「10 張表 × 2 個映射方向 × 5 個 key 偏移」,用可列印 ASCII 比例
排序。正確組合自己會浮出來,不需要任何內容假設:

```
100.0%  table3    index   offset=n+1
 43.6%  table7    forward offset=n+1
 ...
```

`n = 11`,而 `11 % 4 = 3` —— 正是文件寫的規則。**一跑就同時證明了演算法是對的、
以及 blob 裡根本沒有 `LaunchTicket`**,兩個結論一次到手。

這條原則(真實位元組抓一次 → 轉成離線 fixture)本來就寫在 `src/dev/capture.ts` 的
註解裡,這次只是又付了一次學費才想起來用。

## 兩條路都在真實伺服器上通過了

換一個遊戲再跑一次探針,就得到了另一半 —— **同一份 code、同一個 session、同一分鐘,
兩個遊戲落在兩條不同的路上,而且都成功。**

| | 新瑪奇 Mabinogi(`600309_A2`) | 新楓之谷 MapleStory(`610074_T9`) |
| --- | --- | --- |
| `m_objData` 長度 | 697 | 553 |
| 解碼欄位 | `ppppp`, ServiceCode, ServiceRegion, ServiceAccount, **CreateTime**, BeanfunUrl, WebStartPatch | **`LaunchTicket`**, ServiceCode, ServiceRegion, ServiceAccount, BeanfunUrl, WebStartPatch |
| 路由 | legacy | **v2** |
| legacy 端點回應 | `Secret codes do not match!`(用錯 secret 時) | **`Query String Error`(兩種 secret 都一樣)** |
| OTP 長度 | 9 | **10** |
| 結果 | 成功,已登入遊戲 | 成功解出 |

這張表把先前只能靠推論的幾件事變成了量測:

**「拒絕訊息是可診斷的」得到對照組。** 遊戲 B 的 legacy 端點對**兩種 secret 來源都
回 `Query String Error`** —— 那道門真的被封了,跟 secret 對不對無關。遊戲 A 則會因為
secret 來源不同給出不同答案。**同一個客戶端、同一個 session,兩種截然不同的拒絕**,
這是最乾淨的證據。

**上游標記為「未驗證」的那個假設,現在驗證了。** v2 回應的 `data` 確實是同一種
`{8 字元金鑰}{密文 hex}` 信封 —— 解出 10 個可列印字元。上游文件寫著「Implemented,
**not yet run against a live server**」,這點我們可以回報給他們。

**`CV`/`Hash` 這組客戶端驗證值是被接受的**,而且是從一台**完全非 Windows、從未安裝過
GGM** 的主機送出的。上游驗證的是「Windows 但沒裝 GGM」,我們把範圍再推廣了一格。

**OTP 長度不固定**:9 和 10 都出現過,WPF 文件寫 8。**絕對不要寫死長度。**
(瑪奇的 9 碼已實際登入遊戲驗證,不是修剪錯誤。後續普查顯示長度連同一個遊戲都會變
—— 見下節。)

還有一件值得記住的事:**楓之谷正是 BeanyCord 的預設遊戲**
(`DEFAULT_SERVICE_CODE = '610074'`、`DEFAULT_SERVICE_REGION = 'T9'`,WPF 沿用下來的
預設值)。也就是說**新使用者第一個碰到的,就是走 v2 的那一個** —— 如果當初照
「此帳號走不到 v2」把那條路拆掉,預設路徑當場就是壞的。

**`ppppp` 只存在於 legacy 的 blob**;v2 的 blob 沒有它。所以那個欄位是舊流程的殘留,
不是新協定的一部分。

## 四個遊戲的普查:分界線確認了

用 `SERVICE_CODE`/`SERVICE_REGION` 覆蓋(免重新登入)掃過四個遊戲,同一個 session
連續跑完:

| 遊戲 | code_region | `m_objData` | blob 長度 | `ppppp` | `LaunchTicket` | 路由 |
| --- | --- | --- | --- | --- | --- | --- |
| 新楓之谷 MapleStory | `610074_T9` | 有 | 553 | **無** | **有** | **v2** |
| 絕對武力 online (CSO) | `610153_TN` | 有 | 681 | 112 字元 | 無 | legacy |
| 艾爾之光 Elsword | `300148_AF` | 有 | 697 | 112 字元 | 無 | legacy |
| 新瑪奇 Mabinogi | `600309_A2` | 有 | 697 | 112 字元 | 無 | legacy |

**四個遊戲全部都有 `m_objData`,但只有一個有 `LaunchTicket`。**

這是本文最重要的一張表。上游的路由條件是「頁面帶了 `m_objData` 就走 v2」——
照那個條件,**這四個遊戲會全部被送到 v2 端點,其中三個必然失敗**。

而這正好對上上游 issue #376 的回報:瑪奇 ❌、CSO ❌、艾爾之光 ❌、龍之谷 ❌、
**楓之谷 ✅**。我們手上的量測與那串回報是同一個現象的兩面。

### `SecretCode` 的修正在三個獨立遊戲上重現

三個 legacy 遊戲的 step 5 掃描結果**完全一致**:

```
secret=page m_strSecretCode       -> 0;        Error: Secret codes do not match!
secret=portal bfSecretCode cookie -> *** OK — ENVELOPE RETURNED ***
```

先前只有瑪奇一個樣本時,還不能排除「這是那個遊戲的怪癖」。三個不同遊戲、不同帳號數
(4 / 12 / 3)、不同 blob 長度,結果一模一樣 —— 這是**系統性行為**,不是巧合。

### 而 v2 遊戲的舊端點對我們能變動的每一個輸入都拒絕

楓之谷,同一次執行的五個 arm:

```
secret=page m_strSecretCode       -> 0;        Query String Error
secret=portal bfSecretCode cookie -> 0;        Query String Error
identity=omitted                  -> 0;        Query String Error
identity=ours (pinned pair)       -> 0;        Query String Error
identity=deliberately wrong       -> 0;        Query String Error
```

(這一頁的 blob 沒有 `ppppp` —— 欄位只有 `LaunchTicket`、`ServiceCode`、
`ServiceRegion`、`ServiceAccount`、`BeanfunUrl`、`WebStartPatch`,沒有 `ppppp`
也沒有 `CreateTime` —— 所以 secret 只掃了兩格而不是四格。)

**同一個客戶端、同一個 session、同一分鐘**,對三個遊戲拿到「換 secret 就會通」,
對第四個拿到「換什麼都不通」。〈拒絕訊息本身是可診斷的〉那張表到這裡就不是推論了,
是有對照組的量測。

順帶記下探針本身的一個修正:身分那三個 arm 在**已遷移的遊戲上沒有意義**,因為舊門
對任何輸入都回同一句話。第一版照跑不誤,還印出一段判讀寫著「omitted 被拒 → 註解是
對的」—— 在這一頁上照字面讀會得到完全相反的結論。現在偵測到 `LaunchTicket` 就跳過
並說明原因。**一個在錯誤情境下仍然輸出答案的量測工具,比沒有工具更危險。**

### 一個被推翻的結論:OTP 長度不是「每個遊戲固定」

先前寫著「OTP 長度會隨遊戲而變」,依據是瑪奇 9 碼、楓之谷 10 碼。

**這次瑪奇拿到 10 碼。** 同一個遊戲、同一個帳號,兩次不同長度。所以正確的說法是
**每次產生的 OTP 長度就可能不同**,跟遊戲無關。

結論不變但理由更強:**絕對不要對 OTP 長度做任何假設** —— 不要寫死、不要驗長度、
不要在 UI 上排版成固定寬度。

### 其他順帶觀察

- `ppppp` 只出現在 legacy 的 blob,且一律 112 字元;v2 的 blob 沒有它
- `unkData` 的 key 在四個遊戲間**相同**(`&seacux55t21133qsetwpzj55`),所以它是
  session 層級而非遊戲層級的值
- 四次探測的帳號數各不相同(4 / 12 / 3 / 1),證明 `getAccounts()` 的 `auth.aspx`
  確實把 portal 切到了指定遊戲 —— 換遊戲真的不需要重新登入

## 尚未驗證的部分

- **v2 路徑拿到的 OTP 尚未實際登入遊戲**(楓之谷)。解密結果形狀正確,但只有真的
  登進去才算數。legacy 那條已經用瑪奇驗證過。
- **CV / Hash 是客戶端驗證關卡**。送出去等於主張自己是官方啟動器。Gamania 一年換
  幾次 GGM,換版當天所有用編譯常數的人會一起壞。**OTP 出現伺服器拒絕時先查這裡**,
  對照上游的 `ggm-client.json`。目前 `CheckVersion.ashx` 回報仍是 `1.5.0.2`。
